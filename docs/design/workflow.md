# 機能を追加するときの UX・UI 設計フロー

練習中のどの場面を改善するかを決め、操作の流れを試してから画面を作る。画面や操作が変わる機能は、着手時に[機能設計テンプレート](feature-template.md)をコピーし、Issue や PR から参照できる場所に置く。仕様の判断、確認結果、保留事項を同じ設計メモに残す。

## 観察から実装まで

Design Council の Double Diamond を、Cube Practice の開発に合わせて使う。検証で前提が崩れたら、課題の定義や操作案まで戻る。[Design Council の Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation)

| 工程                             | 作るもの                                                                                  | レビューで確かめること                                                               |
| -------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Discover — 練習を観察する        | 誰が、どの練習で、何に困るか。既存画面での観察、聞き取り、Issue などの根拠                | 観察したことと仮説を区別できる。根拠が薄い場合は、確かめる方法を決めている           |
| Define — 今回の課題を絞る        | 利用シナリオ、今回の対象、対象外、成功条件                                                | 何ができれば改善と言えるかを、画面名や実装方法に依存せず説明できる                   |
| Develop — 操作案を試す           | 主要フロー、必要な例外、ワイヤーフレームまたはプロトタイプ、比較した案と採用理由          | スマホ幅とキーボードで操作を追える。代表タスクを試し、迷った箇所と修正を記録している |
| Deliver — 仕様を実装して確かめる | 確定した画面と状態、UI 文言、既存トークンやコンポーネントとの差分、受け入れ条件、確認結果 | 設計メモから実装と検証結果をたどれる。公開後に見直す観点を記録している               |

ラベルや余白だけの修正なら、変更理由と確認結果を PR にまとめる。計測、保存、画面遷移に関わる変更は、影響する状態と操作を設計メモで追えるようにする。

## 操作フローと UI の引き渡し

1. 練習開始から次のソルブまでをつなげて描く。練習中に使う情報と、停止後に見返す情報の優先順位を決める。
2. 通常時と、機能に関係する準備中、空、無効、失敗、復帰を描く。タップとキーボードの入力、表示文言、フォーカスの移動先、保存の時点を決める。
3. [現行 UI の仕様](current-ui.md)を見て、既存のレイアウトや操作で表現できる箇所を確認する。配色・文字・部品の追加は[デザインシステムの導入計画](design-system.md)に沿って検討する。
4. 代表タスクを試し、完了できたか、途中で迷った操作、次の練習に戻れたかを記録する。自分で試した結果と利用者の反応は、参加者と条件を添えて記録する。

## PR で確認すること

- [ ] 設計メモと実装が対応し、主要フローと影響する例外の確認結果がある
- [ ] 狭い幅と広い幅で、時間が長い場合や記録が多い場合も主要操作と情報が隠れない
- [ ] タップとキーボードで操作でき、フォーカスが見える。状態を色と文言など複数の手掛かりで判別できる
- [ ] 文字と必要な UI のコントラスト、操作領域、拡大時の表示、動きを減らす設定を、変更範囲に応じて確認した
- [ ] Next.js の変更を next-dev-loop スキルで実行時に確かめ、リポジトリルートで `pnpm check` を実行した
- [ ] UI 仕様や共有トークンを変えた場合、対応する文書と必要なキャプチャを同じ PR で更新した

Web のアクセシビリティレビューは WCAG 2.2 AA を目安にする。主な参照先は [色の使用](https://www.w3.org/TR/WCAG22/#use-of-color)、[文字のコントラスト](https://www.w3.org/TR/WCAG22/#contrast-minimum)、[UI のコントラスト](https://www.w3.org/TR/WCAG22/#non-text-contrast)、[リフロー](https://www.w3.org/TR/WCAG22/#reflow)、[フォーカスの可視化](https://www.w3.org/TR/WCAG22/#focus-visible)、[ターゲットの最小サイズ](https://www.w3.org/TR/WCAG22/#target-size-minimum)。

## 設計メモの記入例

ロードマップにある「練習モード」を題材にした仮案。実際に着手するときは、[機能設計テンプレート](feature-template.md)から設計メモを作り、調査結果に合わせて仮案を見直す。

| 項目           | 記入例                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| 課題の仮説     | 通常ソルブと X-Cross を続けて練習すると、見返すときにどの練習の記録か区別しづらい                          |
| 代表タスク     | X-Cross を選ぶ → 計測する → 停止する → 履歴でモードを確かめる → 次の計測に進む                             |
| 比較する案     | 計測前にモードを選ぶ案と、停止後に記録へモードを付ける案。途中で練習を切り替えたときの手数と誤登録を比べる |
| 成功条件の案   | 代表タスクで、スマホとキーボードのどちらからも意図したモードの記録を見つけ、次の計測に進める               |
| 先に決める仕様 | 計測中のモード変更、従来の記録の見え方、再読み込み後の選択状態、誤ったモードで保存したときの扱い           |
